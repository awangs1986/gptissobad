# 翻译总策略（最高级别）

本文凌驾仓库内一切与之冲突的旧结论，特别是
`docs/spec/han-blocking-and-cache.md` 的 fail-closed 部分。
冲突处以本文为准，旧文保留只读作历史。

## 0. 前提（已更正）

上游收到中文的后果是**限流**（社区确认），不是封号。旧设计按封号做的
fail-closed 大厦从此降级：**宁可被限流，不可在本地一直 403**——403 到
用户手里等于产品关机。

## 1. 翻什么，不翻什么

- 翻译正文：POST 的 user 与 assistant 文本走翻译；
- 以下**不翻译，直接放行**：路径、AGENTS.md、术语、约束类文档、工具输出、
  instructions / developer 消息、查询串、请求头、解不开的请求体。

## 2. 必须 LLM 翻译

不做机翻（规则替换）。一律给 Translator Backend（MIMO）发指令翻译，
`temperature: 0`，指令含永不作答。

## 3. 内容侧失败不断轮，直接放行

历史、工具输出、指令、文档、查询串、请求头、解不开的包里带中文：不断轮，
原文照样打到上游。中文因此可能到达上游——这是本策略 conscious 的选择
（见 §0），不是泄漏事故，不必报修。

例外：翻译器**交白卷**（HTTP 200 但回中文）仍然 403，见 Q2。交白卷说明
连英文化的版本都不存在，放行等于把用户原话裸奔，没有任何收益。

## 4. 回复指令放最前面，中英同

首条 user 文本之前即要求中文回复（`Please reply in Chinese.`），中文轮
英文轮一致，只放一份，不叠加。

## 5. 什么时候 403，什么时候放行原文

403 只三种：

1. 额度用完（Translator 返回 429/402，正文点名“额度”）；
2. 翻译器故障（含模型调用失败：超时、5xx、4xx、非法返回；交白卷单列，见 Q2）；
3. opencode go 连接不上。

以下不断轮，原样放行、不翻译、不记翻译 token：整轮几乎全是密钥行、密钥行
带中文、没配翻译密钥。凭据行永远不进翻译器；同轮其他正文照常翻译，指令照贴。

传输层例外（与内容无关，保留）：WebSocket 一律 403（看不见的传输不能代理，
只能拒绝）；前置探不到真网关时回 403（否则是连接被拒，更差）；上游建连
10 秒、首字节 180 秒超时回 403（否则一个挂掉的上游占住连接直到客户端放弃）。

## 6. 尺寸与上下文（最优化目标：能翻就一定翻，翻不动就少翻、别断轮）

### 6.1 一次翻译请求有多大

两把尺子同时管，谁先到谁切：

- `MaxChunkRunes`（默认 1500 字符）：按换行打包，单行超限在 rune 边界硬切，
  第一片带换行、其余不带（不会凭空造换行）；
- `MaxChunkTokens`（默认约 2000 token，估算）：防止把 `MaxChunkRunes` 调大
  以后把一片塞不进翻译模型的窗口。估算故意**偏大**（Han/假名/谚文按 1 rune
  = 1 token，ASCII 按 3 字符 = 1 token），宁可多切一刀。

一片被翻译服务以「太大」拒绝（HTTP 400 带 context/length 字样、413）时，
网关**对半切开重试**（优先在换行处切，否则按 rune 中点切），最多 3 层
（1500 → 750 → 375 → 188）。切不动了才是真配置错误，那时按 403 处理并写明
「文本超出翻译服务的上下文」。这种尺寸错误**不再浪费一次备用模型调用**：
同样的字节换一个模型也是同样的大小。

### 6.2 中文装得下、译文装不下怎么办

这是真实存在的：中文 token 密度和英文不一样，同一个请求翻成英文可能变长。
所以 Control Page 有「上游上下文上限」（tokens，0 = 不检查，即默认行为）：

- 开启后网关先估算「翻译完的这份请求」有多大（已知缓存条目按**实测**长度算，
  没翻过的按 +25% 估），超过上限的 90% 才动手；
- 超了就从**最老**的可翻译文本开始放弃翻译，原文照发（§0/§3 的既有选择），
  一直减到装得下；
- **最新一轮永远翻译**：翻不着东西等于把用户当前的提问裸奔，那是这个项目最
  不想看到的结果，比超一点点上下文更糟；
- 请求本身（还没翻译）就超上限时不做任何妥协：翻译不是原因，减了也没用，
  照常翻，日志里说明白；
- 每次真的放弃都会写日志、并计入 Control Page 的「预算放弃」计数。

### 6.3 增量翻译为什么这样做

- 缓存键 = `strategyVersion + 模型 + 翻译指令 + 片段文本` 的哈希。指令进键是
  故意的：改指令等于改输出，不换键就会永远命中旧译文。模型进键让主/备译文
  不互相污染；
- 文件缓存（`~/.codex/translate-cache.json`）**不存原文**，只存「哈希 → 译文」，
  写盘去抖 2 秒、原子替换；超过上限（默认 2 万条）按**插入顺序**淘汰最老的
  —— 长会话里丢掉的是早就翻过去的消息，重新翻一次只花一次钱，不影响正确性；
- 一轮请求内：同一段文本出现两次只翻一次（去重按片段文本）；
- 同一段文本的多个片段**并发**翻译（默认 4 路），顺序在拼装阶段保证，任何
  一片失败就取消其余并在本轮 403；
- 会话前缀匹配（`isPrefix`）只是内存里的第二层，真正省钱的是哈希缓存；
  Codex 压缩历史导致前缀失配时会全量重算，但未变动的片段仍然命中哈希。

已知且不打算改的取舍：片段各自独立翻译，跨片段指代（「上面那段」）会弱一点。
加滑动上下文要多花 token、还会诱发「回答问题而不是翻译」的老毛病，不值。

## 附： grill 记录

- Q1 封号还是限流？答：限流（社区确认）。再 403 等于关机，故有本文。
- Q2 交白卷打上游还是 403？答：先备用到位再 403。主模型**任何翻译失败**
 （回中文、超时、5xx、4xx、连不上）都自动用备用模型（默认
 muse-spark-1.3-contributor，Control 可改、填 - 关闭）按 Responses 方言
 重试一次；备用也不行才按原错误 403（任一侧报额度即点名额度）。备用调用
 同样计 token，Control 单列“备用翻译”计数；备用译文按备用模型键缓存。
- Q3 工具输出翻不翻？答：统一不翻。工具输出是磁盘真实内容，翻完模型看到的
  和文件对不上（搜索替换找不存在的字串）是正确性事故；以后用带标记的遮盖，
  不用翻译。现在维持直放。
